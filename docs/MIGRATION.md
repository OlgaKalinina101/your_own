## Сколько ресурсов нужно

### Память — измерено, не прикинуто

Процесс с `torch` + моделью эмбеддингов + Chroma: **723 МБ RSS**. Это ядро
бэкенда.

| Компонент | РАМ |
|---|---:|
| Python-бэкенд (замер + uvicorn + пики при эмбеддинге) | 1.0–1.5 ГБ |
| PostgreSQL при этом объёме | 0.3–0.5 ГБ |
| Next.js в проде (`next build` + `next start`) | 0.2–0.3 ГБ |
| ОС | 0.3–0.5 ГБ |
| **Итого рабочих** | **~2.5–3 ГБ** |

**4 ГБ — минимум, 8 ГБ — комфортно.**

⚠️ **Важно:** `npm run electron:dev` поднимает `next dev` с
`--max-old-space-size=4096`. На сервере так нельзя — нужен `next build` один раз
и `next start`. Иначе одна только сборка съест 4 ГБ.

### Процессор

Эмбеддинги считаются на CPU в пуле потоков (синхронный torch, вынесен из
event loop специально — иначе он морозит все открытые SSE-потоки).
**2 vCPU хватит, 4 — комфортно.** Видеокарта не нужна: модель маленькая,
384 измерения.

### Диск

| | |
|---|---:|
| Данные | 1.2 ГБ |
| Окружение (venv + node_modules) | 2.2 ГБ |
| Модель | 1 ГБ |
| ОС | ~3 ГБ |
| **Занято сразу** | **~7.5 ГБ** |

**Рост, посчитанный по факту:**

- `messages`: 7 061 строка за последние 30 дней при 3.84 КБ на строку → **~27 МБ/мес**
- корпус вызовов: ~7–10 МБ/мес после gzip (сжатие 4.2×)
- фотографии: сколько будет, это от вас

Итого база и корпус — **около 0.5 ГБ в год**. **40 ГБ диска хватит на годы**,
25 ГБ — рабочий минимум.

> На нынешней машине свободно **3.3 ГБ** из 476. Это само по себе довод
> переезжать: корпус растёт, а места под него уже почти нет.

## Что нужно кроме железа

### Версии — совпадают, перенос простой

| | Здесь | Нужно на сервере |
|---|---|---|
| PostgreSQL | 17.6 | 17.x |
| pgvector | 0.8.2 | 0.8.x |
| Python | 3.12 | 3.12 |

При совпадении мажорных версий переносится обычным `pg_dump` → `pg_restore`,
без плясок.

### Домен: да, и это дешевле ngrok

**Главное, что я проверил перед этим советом:** адреса картинок в базе —
**относительные** (`/api/user_uploads/...`, 249 строк, ноль абсолютных, ноль с
ngrok). Значит смена адреса ничего не ломает. Единственные три строки с
адресом — в тексте самих сообщений, то есть вы просто упоминали ссылку в
разговоре.

| Вариант | Цена | Что даёт |
|---|---|---|
| ngrok платный | ~$100/год | два зарезервированных домена, третья сторона в пути |
| **Свой домен + Caddy** | **~$12/год** | постоянный адрес, HTTPS сам, никого лишнего |
| Tailscale | бесплатно | приватно, но публичного адреса нет — телефон должен быть в сети |

**Рекомендую: свой домен + Caddy** на VPS с публичным IP. Caddy сам получает и
продлевает сертификат Let's Encrypt, конфиг — пять строк. Дешевле ngrok в восемь
раз, и адрес перестаёт зависеть от чужого сервиса.

Tailscale стоит оставить, но для **SSH**, а не для приложения: тогда порт 22
вообще не смотрит наружу.

Нюанс, который делает вариант с Tailscale тоже рабочим: пуши идут **от сервера
наружу** (Pushy), входящий доступ нужен только чтобы телефон дотянулся до чата.
Если вас устраивает Tailscale на телефоне — публичный адрес не нужен вовсе.

### Резервные копии — то, ради чего всё затевается

Переезд затевался, чтобы перестать бояться за ноутбук. Сервер сам по себе этого
не даёт — он даёт только другое место, где всё лежит. Минимум:

- `pg_dump` раз в сутки, хранить 7–30 копий
- `data/`, `user_uploads/`, `generated_images/`, `infrastructure/vector_store/` —
  раз в сутки
- **копия вне сервера** — иначе один умерший диск снова уносит всё

Измерено: `pg_dump -Fc -Z9` даёт **104 МБ** из 228 МБ базы. Плюс Chroma 55 МБ и
корпус вызовов 99 МБ (он уже сжат) — **ежедневный снимок без фотографий около
260 МБ**. Тридцать копий — 7.8 ГБ.

Фотографии (723 МБ) в ежедневный снимок класть не надо: они не меняются задним
числом, только добавляются. Их правильнее синхронизировать отдельно
(`rsync`/`rclone`), иначе каждая копия тащит те же 723 МБ заново.

## Сервер поднят (AVPS3, 2026-09-02)

`91.198.109.14`, Ubuntu 24.04.1, 4 ядра, 8 ГБ RAM, **77 ГБ диск (свободно 66)**.
Доступ по ключу `~/.ssh/victor_server`, вход по паролю потом отключим.

**Ловушка апгрейда тарифа:** после перехода на AVPS3 RAM и CPU приехали, а раздел
остался 18 ГБ — физический `sda` стал 80 ГБ, но `sda3` не растянули. 62 ГБ висели
неотданными. Чинится на самой машине, без хостера:

```bash
growpart /dev/sda 3
pvresize /dev/sda3
lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
resize2fs /dev/ubuntu-vg/ubuntu-lv
```

С 66 ГБ свободного вся арифметика ниже (где диск был узким местом) больше не
жмёт — торч всё равно ставим CPU-сборкой, но уже ради чистоты, а не выживания.

## Целевой сервер (hayhost.am, замерено 2026-09-02)

| | |
|---|---|
| RAM | 4096 МБ (в простое занято 327 МБ) |
| CPU | 2 ядра, 4788 МГц |
| Диск `/` | 17.83 ГБ, **свободно 9.18 ГБ** |
| ОС | Ubuntu 64-bit |

**Вердикт: тянем. Узкое место — диск, не память.**

### Память проходит с запасом

Рабочее потребление ~2.2 ГБ из 4 (замер ядра бэкенда 723 МБ + uvicorn, Postgres,
`next start`, система). Остаётся ~1.8 ГБ.

### Процессор проходит

Эмбеддинги на двух потоках: **24–26 мс на чанк** (замерено с
`torch.set_num_threads(2)`). Типичный ход — 10–30 чанков, то есть меньше
секунды, и считается в пуле потоков.

Холодный старт модели — **33.8 с**. После перезапуска первое сообщение, которому
нужны векторы, будет ждать. Стоит прогревать при старте.

### ⚠️ Диск: наивная установка НЕ поместится

`torch` на Linux объявляет **15 зависимостей `nvidia-*`**. Только шесть из них
весят **2.58 ГБ** (cudnn 751 МБ, cublas 581, cusparse 366, cusolver 338,
nccl 342, cufft 201) — ради видеокарты, которой на сервере нет.

Обычный `pip install -r requirements.txt` потратит около 3 ГБ на CUDA, и тогда
нужное (≈6.9 ГБ) превысит свободное (9.18 ГБ). Поэтому **обязательно**:

```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
pip install --no-deps -r requirements-nodeps.txt
```

Что займём при правильной установке:

| | ГБ |
|---|---:|
| Данные (с фотографиями) | 1.2 |
| Окружение Python (torch CPU) | 1.2 |
| `node_modules` | 0.95 |
| Модель эмбеддингов | 1.0 |
| Сборка Next (`.next`) | 0.3 |
| Swap | 2.0 |
| PostgreSQL | 0.3 |
| **Итого из 9.18 свободных** | **~6.9** |

Остаётся ~2.3 ГБ при росте 0.5 ГБ/год плюс фотографии. Это ровно то положение,
из которого вы уходите с ноутбука (там свободно 3.3 ГБ). **Если тариф можно
поднять — поднимать надо диск, а не память: 40 ГБ и вопрос закрыт на годы.**

### Обязательное на этой машине

- **Swap 2–4 ГБ.** Без него при пике ядро убьёт процесс, и скорее всего Postgres.
- **`next build` отдельно от работы.** Скрипт разработки просит heap 4096 МБ;
  сборка рядом с работающими Postgres и бэкендом упрётся в потолок. Собирать при
  остановленных сервисах, с `NODE_OPTIONS=--max-old-space-size=1536`, либо
  собирать на ноутбуке и копировать `.next`.
- **Сменить root-пароль и перейти на ключи.** Пароль был виден в панели
  хостинга; VPS с публичным IP перебирают ботами постоянно.
  `PasswordAuthentication no` в `/etc/ssh/sshd_config`.

## Порядок переезда

1. Удалить `data/dataset/calls-2026-08.jsonl.before-cleanup` (52 МБ).
2. Поднять сервер: PostgreSQL 17 + pgvector 0.8, Python 3.12, Node 18+, Caddy.
   Swap 2–4 ГБ. **torch ставить с CPU-индекса** — иначе 3 ГБ CUDA и диск кончится.
3. `pg_dump` → перенести → `pg_restore`. Проверить: 57 007 строк в `messages`,
   54 151 из них с векторами.
4. Скопировать `data/`, `user_uploads/`, `generated_images/`,
   `infrastructure/vector_store/`. RuWordNet можно не копировать — `setup.js`
   скачает.
5. `.env`: поменять `DATABASE_URL`, остальное как есть — машинно-зависимых путей
   в `settings.json` нет (проверено).
6. `next build` + `next start`, **не** `next dev`.
7. Сменить токен доступа: `POST /api/settings/rotate-token`.
8. Прописать новый адрес в телефоне и в десктопе.
9. Настроить резервные копии — до того, как ноутбук выключен, а не после.

> Свободного места на ноутбуке 3.3 ГБ, а перенести надо 1.2 ГБ. Дамп и архив
> одновременно туда не влезут — лучше лить прямо на сервер
> (`pg_dump | ssh сервер psql`), а не собирать архив локально.
